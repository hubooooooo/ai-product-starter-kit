## 0. 进入条件、读什么、产出放哪

**进入条件**：阶段 2 后端 MVP 核心链路已验收（证据包已交，是否表全为"是"或 N/A）。`docs/项目状态.md` 决策台账应已包含目标用户、核心任务、效果标准和登录方式；缺失的按 `AGENTS.md` 第 3 节补问，已定的不再重复问。缺"必须问"类信息（目标用户、核心任务、成本、安全、隐私、交付范围）时先问，不开工。

**AI 自行读取**（不要让产品经理提供或转交任何手册）：

1. `docs/PRD/` 下的 PRD；
2. `docs/阶段文档/技术适配声明.md`，重点看其中对阶段 2 界面的判断；
3. `docs/项目状态.md` 决策台账；
4. 阶段 2 各子阶段的阶段开发文档与接口定义（`docs/阶段文档/`、后端代码里的路由和数据结构）；
5. 现有代码，以及产品经理在对话中给出的设计稿、截图或参考网址。

**先判断阶段 2 留下的界面属于哪一类**（定义见 `AGENTS.md` 第 7 节）：

- **纵向切片界面**（会保留到正式产品）：在它上面继续开发，前端子阶段 1、2 合并，不另起平行工程；
- **临时验收界面**（不会保留）：在第一个前端子阶段把它废弃（删除或停止对外提供入口），并在该子阶段的阶段开发文档里记录废弃了什么；
- **没有界面**：从前端子阶段 1 的可运行骨架开始。

**两份产出**，都存放在 `docs/阶段文档/`，产品经理确认后再编码：

- 《前端适配声明》（模板见第 23 节）：本项目采用什么、为什么、哪些地方偏离默认方案；
- 《第 3-N 阶段开发文档》（模板见第 24 节）：本子阶段做哪些页面、组件、接口、状态和验收。

若 `docs/阶段文档/` 已有前端阶段开发文档，校验并补齐，不另写一套。

**命名约定**：前端子阶段 N（N 从 1 开始；子阶段 0 只产出文档）的证据目录为 `docs/evidence/阶段3-N/`，自检命令为 `./verify.sh 阶段3-N`。

### 产品经理在前端阶段做的事（AI 逐条转述）

1. **给视觉方向**：设计稿、参考产品截图或一个设计系统网址，直接发在对话里，由 AI 保存到 `docs/设计参考/`；都没有的话，AI 按中性方案先做一版代表页。
2. **看代表页反馈**：对颜色、圆角、密度、字体提意见，AI 改到满意再铺开全站，避免改错返工。
3. **逐子阶段验收**：AI 每完成一个闭环，给"照着点"清单（打开哪个地址、点哪几步、看到什么算对），产品经理照做，把异常截图发给 AI。
4. **真机验证**：用自己的手机（含 iPhone）走一遍核心流程；涉及麦克风、摄像头的，先按第 10.5 节的步骤在手机上信任本地证书。

## 1. 本手册解决什么问题

普通技术栈清单只会告诉 AI“使用 Next.js、React、Tailwind CSS”。这远远不够。

AI Agent 产品的前端还要处理：

- 一个任务可能运行几秒、几分钟甚至更久；
- 生成过程可能持续输出文本、步骤、日志和中间结果；
- Agent 可能暂停，等待用户确认或补充资料；
- 页面刷新、断网或关闭后，任务仍可能在后端继续运行；
- 同一个任务可能产生图片、视频、音频、文件等不同产物；
- 接口成功不等于产品成功，用户必须看得懂当前发生了什么；
- 桌面端能用，不代表移动端、键盘操作和异常状态能用；
- “构建成功”不等于“页面已经达到交付标准”。

因此，本手册同时规定四件事：

1. 默认技术栈；
2. 前端架构和数据边界；
3. Agent 交互与任务状态规范；
4. 开发、预览和验收规范。

---

## 2. 适用边界

### 2.1 默认适用

- AI 对话、内容生成、工作流、自动化和多媒体生成产品；
- 内部工具、运营后台、创作工作台、Agent 控制台；
- 面向桌面浏览器，兼顾移动浏览器的 Web MVP；
- 从零创建的新项目；
- 已有 React 或 Next.js 项目的功能迭代。

### 2.2 可以参考，但不能直接照搬

- 原生 iOS、Android、鸿蒙应用；
- 微信小程序、桌面客户端、浏览器插件；
- 对搜索引擎收录、极致首屏速度有特殊要求的大型内容站；
- 高实时协同编辑、3D、游戏、超大数据可视化产品；
- 受医疗、金融、政务等强监管约束的系统。

遇到这些场景，仍需遵守本手册的状态、安全和验收原则，但 AI 必须在《前端适配声明》中重新说明技术选择，不能机械套用 Web 默认栈。

## 3. 不能因为 PRD 没写就忽略的事

资料冲突时的优先级见通用技术栈手册第二节"与 PRD 的配合契约"；安全与验收底线以 `AGENTS.md` 为准。以下前端事项不能因为 PRD 没写就忽略：

- 安全和隐私底线；
- 加载、空、失败和恢复状态；
- 移动端基本可用；
- 核心流程的真实浏览器验收；
- 不得在前端暴露密钥；
- 不得把本地界面状态冒充为后端真实任务状态。

资料存在关键冲突时，AI 在编码前用产品语言说明冲突、影响和推荐方案，不在代码中偷偷选择。

## 4. 决策分层：哪些必须统一，哪些按项目选择

### A 层：所有项目都必须遵守

- 使用 TypeScript，并开启严格类型检查；
- 接口调用集中管理，不在页面组件中散落 `fetch`；
- 后端是任务状态和业务结果的最终事实来源；
- 加载、空、成功、失败、等待确认、断线恢复等状态必须被设计；
- 密钥、服务商凭证、私密系统提示词不能进入浏览器；
- 核心页面必须支持合理的桌面端和移动端布局；
- 核心操作可被键盘完成，交互控件有可理解的名称；
- 重要提交必须防重复，重要删除必须确认；
- 必须通过代码检查、构建检查和真实浏览器验收；
- 不能只用 Mock 数据宣布“前后端已经完成”。

### B 层：Web MVP 默认方案

- Node.js 当前活跃 LTS 版本；
- npm 作为默认包管理器；
- Next.js 稳定版本，使用 App Router；
- React 与 Next.js 官方支持的稳定版本；
- TypeScript strict 模式；
- Tailwind CSS + CSS 语义变量；
- Lucide 图标；
- Vitest + React Testing Library；
- ESLint、类型检查、生产构建作为交付门槛。

版本一律取建项目时的稳定版：Node.js 取当时的 Active LTS，Next.js、React、Tailwind CSS 取当时的稳定大版本。手册不写死版本号；在《前端适配声明》中记录实际使用的版本，并锁定依赖文件。

### C 层：出现明确需求后再引入

| 能力 | 建议方案 | 引入条件 |
|---|---|---|
| 无障碍复杂组件 | Radix UI 或基于它的 shadcn/ui | 对话框、菜单、下拉框等组件较多 |
| 服务端数据缓存 | TanStack Query | 多页面共享请求、缓存、失效和重试变复杂 |
| 全局客户端状态 | Zustand | 多个远距离组件共享临时状态，URL 和组件提升都不合适 |
| 复杂表单 | React Hook Form + Zod | 动态字段、多步骤表单、复杂校验 |
| 接口代码生成 | OpenAPI Generator 等 | 后端已有稳定、可持续维护的 OpenAPI 契约 |
| 大列表虚拟化 | TanStack Virtual 等 | 实际数据量造成明显卡顿 |
| 富文本或代码编辑器 | 按业务选型 | PRD 确实需要编辑能力 |
| 图表、画布、流程编排 | 按业务选型 | PRD 出现对应交互，不提前预装 |
| 国际化 | 成熟 i18n 方案 | 已确认多语言需求 |
| PWA、离线能力 | Service Worker 方案 | 已确认离线或安装需求 |
| 前端错误监控 | Sentry 等 | 产品进入真实用户测试或生产环境 |
| 产品行为分析 | 合规的分析工具 | 已有指标方案和用户授权策略 |
| 端到端自动化测试 | Playwright | 核心闭环超过 2 条，或同一闭环反复回归、人工"照着点"成本明显上升 |

表中的第三方服务（如 Sentry、产品行为分析工具）可能计费，引入前按 `AGENTS.md` 第 2 节第 8 条先告知产品经理费用量级，等确认后再接入。

原则：没有真实复杂度，就不要用复杂工具制造“看起来专业”的代码。

## 5. 默认技术选型

### 5.1 应用框架：Next.js App Router

默认选择 Next.js，而不是自己拼装 React 路由、构建、服务端渲染和部署能力。

适合 Agent 产品的原因：

- 页面路由、布局和服务端能力在同一个工程中；
- 可以按页面决定服务端组件和客户端组件；
- 方便实现同源 API 代理、鉴权入口和部署；
- 生态成熟，AI 对代码结构和常见问题的识别能力较强。

以下情况可以改用其他方案：

- 已有项目已经稳定运行在其他框架；
- 产品只需要一个很小的嵌入式页面；
- 部署平台对框架有明确限制；
- 原生端或小程序不是 Web 技术路线。

AI 不得仅为了“追新”而替换已有稳定框架。

### 5.2 语言：TypeScript strict

最低要求：

- 核心业务类型不使用 `any` 逃避检查；
- 外部接口返回值在进入业务层前被约束或校验；
- 组件 Props、任务状态、产物类型、错误类型有清晰定义；
- 使用 `unknown` 接住不可信数据，再逐步缩小类型；
- 类型错误不能以“先忽略”为交付方案。

TypeScript 只能检查开发时类型，不能证明后端实际返回的数据正确。关键外部数据仍需运行时校验或安全的字段兜底。

### 5.3 样式：Tailwind CSS + 语义化设计变量

Tailwind CSS 负责快速布局和原子样式，CSS 变量负责统一设计语言。

颜色、圆角、阴影、间距等应尽量表达语义，例如：

```css
@import "tailwindcss";

@theme {
  --color-bg: #ffffff;
  --color-surface: #f7f8fa;
  --color-text: #18202a;
  --color-muted: #667085;
  --color-primary: #5b5ce2;
  --color-danger: #d92d20;
  --radius-card: 16px;
}
```

Tailwind CSS 4 起，写在 `@theme` 里的变量会生成对应工具类（如 `bg-surface`、`rounded-card`）；`:root` 里的变量不会生成工具类，只用于运行时切换的值（如深色主题覆盖）。仍在 Tailwind 3 的已有项目沿用其 `tailwind.config` 写法。

不要让页面各处直接散落无法解释的颜色值，也不要把 Tailwind CSS 本身当成完整设计系统。

### 5.4 组件策略

默认顺序：

1. 先复用当前项目已有组件；
2. 再使用原生 HTML 和轻量自建组件；
3. 复杂交互组件使用成熟的无障碍基础组件；
4. 只有确有必要时才引入完整组件库。

组件库解决的是交互基础和开发效率，不负责替产品做视觉设计。

### 5.5 版本策略

- 新项目创建时选择稳定且仍受维护的版本；
- 在 `package.json` 和锁文件中固定实际依赖；
- 同一开发阶段内不主动跨大版本升级；
- 安全修复可以升级，但升级后重新执行完整检查；
- 已有项目优先兼容，不因为本手册的参考版本而强制迁移。

## 6. 默认前端架构

### 6.1 推荐目录

新项目默认使用“路由 + 业务功能 + 通用基础设施”的结构：

```text
frontend/
├── app/                       # 路由、页面、布局、错误页
│   ├── (workspace)/
│   ├── bff/                   # 仅当需要 BFF 逻辑时创建；不要占用被 rewrites 代理的 /api/* 路径
│   ├── error.tsx
│   ├── loading.tsx
│   └── layout.tsx
├── components/
│   ├── ui/                    # Button、Dialog、Input 等通用组件
│   └── layout/                # 顶栏、侧栏、页面容器
├── features/
│   └── task-generation/       # 按业务功能组织
│       ├── api/
│       ├── components/
│       ├── hooks/
│       ├── schemas/
│       ├── types.ts
│       └── utils.ts
├── lib/
│   ├── api/                   # API 客户端、错误归一化
│   ├── stream/                # SSE 或流式响应处理
│   ├── auth/
│   ├── media/
│   └── utils/
├── config/                    # 环境与产品配置
├── styles/                    # 全局样式和设计变量
├── tests/                     # 单元与集成测试
└── e2e/                       # 引入 Playwright 后才创建（见第 4 节 C 层）
```

这是一种默认思路，不是强制要求已有项目重构目录。

### 6.2 依赖方向

```text
页面路由
  ↓
业务功能组件与 Hook
  ↓
API / Stream / Auth 适配层
  ↓
后端接口
```

通用 UI 组件不应反向依赖某一个具体业务。页面组件不应直接理解不同后端供应商的特殊字段。

### 6.3 新项目与已有项目的处理

新项目：按本手册默认架构建立基础骨架。

已有项目：先理解已有目录、命名和依赖，再做最小范围改动。除非重构本身是本阶段目标，否则不要一边开发业务，一边大规模迁移目录和组件库。

## 7. 页面渲染与路由选择

### 7.1 Server Component 与 Client Component

Next.js App Router 默认使用 Server Component。

适合 Server Component 的内容：

- 静态说明和帮助页面；
- 首屏即可从服务端获取的数据；
- 不依赖浏览器事件和本地状态的展示；
- 对搜索引擎或分享预览有要求的页面。

适合 Client Component 的内容：

- 表单、拖拽、弹窗和复杂交互；
- Agent 实时进度、流式输出和任务控制；
- 依赖浏览器 API、Local Storage 的功能；
- 高频变化的工作台区域。

不要因为一个按钮就把整页都声明为客户端组件。应把交互边界缩小到必要区域。

### 7.2 URL 是可分享状态的首选

以下状态优先放入路由或查询参数：

- 当前项目或任务 ID；
- 当前工作区、标签页和筛选条件；
- 可以被复制、刷新和恢复的查看位置。

以下状态不适合放 URL：

- 输入框每个按键的临时值；
- 弹窗内部未提交数据；
- 凭证和隐私信息；
- 大体积对象。

刷新页面后，前端应能根据 URL 中的任务 ID 向后端恢复真实状态，而不是依赖内存中残留的数据。

### 7.3 避免 Hydration 问题

浏览器专属信息不能直接参与服务端首次渲染。例如屏幕宽度、Local Storage 和浏览器语言应在客户端安全读取，并提供稳定的首屏默认值。

移动端侧栏、主题和个性化设置必须确保 CSS、React 状态和持久化状态一致，不能出现“按钮显示已经收起，但遮罩或侧栏仍挡住页面”的情况。

## 8. 前端状态管理：先分清四种状态

### 8.1 状态分层

| 状态类型 | 例子 | 默认存放位置 |
|---|---|---|
| URL 状态 | 任务 ID、当前页签、筛选 | 路由或查询参数 |
| 服务端状态 | 任务进度、产物、权限、余额 | 后端；前端通过 API 获取 |
| 页面临时状态 | 输入内容、弹窗开关、局部选中 | 组件 State 或局部 Context |
| 用户偏好 | 主题、侧栏偏好、非关键提示已读 | Local Storage 或用户配置接口 |

### 8.2 事实来源

- 后端任务状态是最终事实来源；
- Local Storage 不能保存并冒充真实任务结果；
- 页面刷新后应重新拉取任务，而不是默认任务失败；
- 同一个任务的不同页面应使用同一个状态定义；
- 前端可以做乐观更新，但失败时必须能回滚。

### 8.3 什么时候引入状态库

默认先使用 React 自带状态能力。

只有出现以下问题时，再引入 TanStack Query：

- 多个页面共享相同服务端数据；
- 请求缓存、失效和重试逻辑重复；
- 列表分页、预取和后台刷新明显复杂；
- 手写请求状态已经难以维护。

只有出现以下问题时，再引入 Zustand 等客户端状态库：

- 多个距离很远的组件共享大量临时状态；
- 状态与 URL、后端数据都无关；
- 通过层层传 Props 已明显降低可维护性。

不要一开始同时引入 Context、Redux、Zustand 和 TanStack Query。

## 9. Agent 产品必须有统一任务状态模型

### 9.1 最低状态集合

一个长任务至少要考虑以下状态：

| 统一状态 | 用户看到什么 | 前端需要做什么 |
|---|---|---|
| `idle` | 尚未开始 | 显示输入和可执行条件 |
| `submitting` | 正在提交 | 禁止重复提交，允许取消请求 |
| `queued` | 已进入队列 | 显示任务已受理，不伪装成正在生成 |
| `running` | 正在执行 | 显示真实进度、阶段或活动提示 |
| `streaming` | 正在持续输出 | 增量展示，避免页面频繁跳动 |
| `waiting_user` | 等待用户确认或补充 | 明确需要用户做什么、为什么 |
| `succeeded` | 已完成 | 展示产物和下一步操作 |
| `partially_succeeded` | 部分成功 | 清楚区分成功项和失败项 |
| `failed` | 执行失败 | 说明发生了什么、是否可重试 |
| `cancelled` | 已取消 | 保留已有信息，允许重新开始 |
| `disconnected` | 连接中断 | 说明任务未必停止，尝试恢复 |
| `stale` | 状态可能过期 | 主动重新获取后端真实状态 |

后端可以使用不同名字，但前端必须在适配层映射成统一含义。未知状态不能静默当成成功或失败，应记录并显示安全的兜底状态。

### 9.2 状态不是一个转圈图标

每个状态都应回答用户三个问题：

1. 现在发生了什么？
2. 我需要做什么？
3. 接下来会发生什么？

例如，“生成失败”不够。更好的表达是：“视频合成失败，已生成的分镜仍然保留。你可以重新合成，不会重复扣除前一步结果。”

### 9.3 加载、空数据和失败必须分开

- `loading`：数据还没回来；
- `empty`：请求已经成功，但确实没有数据；
- `failed`：请求没有成功；
- `permission_denied`：用户无权查看；
- `not_found`：对象不存在或已被删除。

不能在接口尚未返回时先显示“暂无模板”“暂无任务”。这种瞬时错误信息会让用户误以为系统没有数据。

## 10. 流式输出、轮询和断线恢复

### 10.1 选择顺序

| 场景 | 默认方案 |
|---|---|
| 服务端单向持续推送文本或进度 | SSE 或 Fetch Streaming |
| 浏览器与服务端需要双向高频通信 | WebSocket |
| 后端暂时只支持状态查询 | 有节制的轮询 |
| 只需等待一个普通短请求 | 普通 HTTP 请求 |

不要为了“实时感”强行使用 WebSocket。

### 10.2 SSE 注意事项

- 原生 `EventSource` 适合 GET 请求，但不方便设置自定义请求头；
- 需要 POST、请求体或特殊鉴权时，可使用 Fetch Streaming；
- Cookie 鉴权优先通过同源接口处理；
- 某些代理会缓存响应，必须在真实部署链路验证是否逐段到达；
- 页面卸载、任务切换和取消时要关闭连接；
- 断线后应按任务 ID 查询状态，再决定重连，不能盲目重复创建任务；
- 后端 SSE 一定以 `done` 或 `error` 事件收尾（`AGENTS.md` 第 2 节第 3 条）。前端收到 `error` 映射为 `failed`，展示其中的 `message`；连接关闭但没收到 `done` 映射为 `disconnected`，按任务 ID 回查后端状态；不得把没有 `done` 的关闭当成成功。

### 10.3 轮询注意事项

- 使用明确间隔和退避策略；
- 页面不可见时降低频率或暂停；
- 完成、失败、取消后立即停止；
- 避免每个组件各自轮询同一任务；
- 接口失败时不要无限高频重试。

### 10.4 增量展示

- 流式文本要批量刷新，避免每个字符触发复杂重渲染；
- 自动滚动只在用户仍停留在底部时发生；
- 用户向上查看历史内容时，不强行把页面拉回底部；
- 日志、思考过程和用户可见结果要分层，不把内部敏感信息直接展示；
- 断线重连后应去重，避免重复追加相同内容。

### 10.5 语音与实时多媒体交互（语音对练 / 语音问答类产品）

当核心交互是**实时语音**时，除了文本流，还要处理"音频流"。链路：

```text
麦克风录音 → 上传 → 后端 ASR 转写 → Agent 生成回复 → TTS 合成 → 音频流回传 → 前端播报
```

前端必须额外处理：

1. **麦克风授权是生死关**：浏览器只在 HTTPS 或 localhost 下开放麦克风权限。手机通过局域网地址（如 `http://192.168.x.x:3000`）访问时既不是 HTTPS 也不是 localhost，麦克风会被直接拒绝，真机验收按下方"本地 HTTPS 真机验收"处理。授权被拒要给明确引导，不能静默失败；未授权不开始录音。
2. **音频流播报**：音频分片和文本分片的事件名、编码以阶段 2 的接口定义为准，例如后端通过 SSE 分别推送文本事件和 base64 编码的音频分片事件，两者是并行的两条流。用 Web Audio API 把音频分片按时间轴排队播放，避免重叠；会话结束或切换时重置队列。
3. **iOS / Safari 兼容**：`MediaRecorder` 在不同浏览器支持的容器格式不同——Chrome 是 `webm/opus`，iOS/Safari 是 `mp4/aac`。要运行时探测 mime，并把实际格式随上传告诉后端。
4. **交互从简**：MVP 优先"回合制对讲机"（按下说话、再按发送）；全双工 + barge-in 打断是后续阶段。
5. **会后回放**：整段回放 + 逐句点播。默认 Cookie 鉴权（第 18.2 节）下，同源的 `<audio src>` 会自动带上 Cookie，可以直接使用；只有后端要求 Bearer 请求头时，才用 fetch 取回 blob、生成 Object URL 播放，用完 `revokeObjectURL`。

**本地 HTTPS 真机验收**（阶段 3 还没上线时）：

- 不涉及麦克风、摄像头的功能：手机和电脑连同一个 Wi-Fi，用局域网地址访问即可。
- 涉及麦克风、摄像头的功能：Next.js 自带的 `next dev --experimental-https` 生成的证书只覆盖 localhost，手机访问局域网 IP 时仍会报不安全。AI 用 mkcert 为电脑的局域网 IP 签发证书，再用 `next dev -H 0.0.0.0 --experimental-https --experimental-https-key <key 文件> --experimental-https-cert <证书文件>` 启动。然后给产品经理下面的"照着点"步骤：
  1. AI 把 mkcert 的根证书文件 `rootCA.pem` 通过隔空投送、微信文件或邮件发到手机。只发这一个文件，绝不发 `rootCA-key.pem`。
  2. iPhone：在手机上打开这个文件，按提示允许下载描述文件；到"设置"里点"已下载描述文件"并安装；再到"设置 → 通用 → 关于本机 → 证书信任设置"，打开这张证书的完全信任开关。
  3. Android：到"设置 → 安全 → 加密与凭据 → 安装证书 → CA 证书"，选中这个文件。不同品牌菜单名略有差异，找不到就截图发给 AI。
  4. 用手机浏览器打开 AI 给的 `https://192.168.x.x:3000`，页面正常打开、地址栏没有"不安全"提示，就算成功。
  5. 验收结束后，AI 提醒产品经理在手机上删除这张证书。
- 做不到时（手机无法安装证书、设备受公司管控等）：该项在阶段开发文档和是否表说明里如实记为"待上线后验"，不得写成已验证。

**验收**：真实手机（含 iPhone）按上面的方式走一遍录音→播报→回放；会中不出现评分、答案等无关信息；断网或离开页面后已完成的轮次仍然保留。

## 11. 用户确认、重试、取消和恢复

### 11.1 等待用户确认

当 Agent 等待用户决定时，界面必须展示：

- 当前已经完成了什么；
- 为什么需要确认；
- 可选项及各自影响；
- 默认推荐项；
- 确认后是否可撤销；
- 放弃或返回的方式。

“继续”和“取消”之外，应尽量使用有业务意义的按钮，例如“采用这版分镜并生成视频”。

### 11.2 防止重复提交

- 点击后立即进入明确的提交状态；
- 同一操作在完成前不可重复触发；
- 后端配合使用幂等键；
- 网络超时时，先查询原任务是否已创建，再决定是否重试；
- 禁止用多次点击产生多个昂贵的模型任务。

### 11.3 取消

前端的“取消请求”与后端的“取消任务”不是同一件事。

- 取消浏览器请求：只停止等待；
- 取消后端任务：需要后端提供真实取消能力；
- 如果后端不能取消，按钮应写“停止等待”或“离开页面”，不能误导用户。

### 11.4 恢复

用户刷新页面、关闭页面或重新登录后：

1. 通过 URL 或任务列表找到任务 ID；
2. 向后端查询真实状态；
3. 恢复已有中间结果和产物；
4. 仅在任务仍运行且协议允许时恢复流式连接；
5. 不重复创建同一个任务。

## 12. API 与后端契约

### 12.1 集中式 API 层

前端只通过后端 API 调用业务能力：模型调用、业务规则和权限判断都在后端，前端不直连模型服务，也不在 Next.js 服务端代码里复制后端业务逻辑。

不破坏阶段 2 已验收的后端接口契约。前端需要后端做不兼容修改时（改字段名、改状态值、改错误码），先说明受影响的调用方、已有数据和迁移办法，经产品经理确认后再改，并同步更新阶段 2 的 mock 测试（`AGENTS.md` 第 2 节第 9 条）。

页面不直接拼接接口地址。基础 URL、鉴权、超时、错误转换和日志应集中处理。

```text
UI 组件
  ↓ 调用业务函数
Feature API
  ↓ 调用统一客户端
HTTP / Stream Client
  ↓
Backend API
```

这样可以避免：

- 开发环境和生产环境地址散落；
- 普通请求与流式请求使用不同配置；
- 每个页面用不同方式解释错误；
- 后端字段改名导致所有组件同时修改。

### 12.2 最低接口契约

每个接口至少明确：

- 请求方法和路径；
- 请求字段、类型、是否必填；
- 成功返回结构；
- 失败错误码和用户可恢复方式；
- 鉴权与权限要求；
- 是否幂等；
- 超时和重试策略；
- 任务 ID、状态和产物字段；
- 时间、枚举、金额和文件地址的格式。

### 12.3 统一错误结构

后端错误体固定为 `{"error": {"code", "message"}}`（`AGENTS.md` 第 2 节第 3 条）。前端适配层据此生成下面的 `AppError`，不另造错误协议；`userMessage` 由前端按 `code` 映射成产品语言，未知 `code` 用通用兜底文案：

```ts
type AppError = {
  code: string;
  message: string;
  userMessage: string;
  retryable: boolean;
  requestId?: string;
  fieldErrors?: Record<string, string>;
};
```

用户界面显示 `userMessage`，调试日志保留 `code` 和 `requestId`。不要把原始堆栈、供应商报错或敏感请求内容直接展示给用户。

### 12.4 接口类型来源

- 后端已有稳定 OpenAPI：优先生成类型和客户端；
- 契约仍快速变化：先维护清晰的手写类型和适配层；
- 无论哪种方式，生成代码外再保留业务适配层；
- 前后端枚举变化必须有未知值兜底。

### 12.5 环境配置

- 浏览器可读配置可以使用 `NEXT_PUBLIC_`；
- API 密钥、模型密钥、数据库凭证绝不能使用 `NEXT_PUBLIC_`；
- 前端环境只保存公开配置；
- 开发、测试、生产环境地址通过配置管理；
- 普通 API 与流式 API 的地址策略必须一致并经过部署验证；
- 前后端同源的默认做法是用 `next.config` 的 `rewrites` 把 `/api/*` 代理到 `BACKEND_URL`，避免跨域；`app/` 下不再建同名的 `/api` 路由；
- 前端本地配置写在 `frontend/.env.local`，必须被 `.gitignore` 排除（根目录 `verify.sh` 会扫描这个文件里的值有没有泄露）；仓库只提交 `frontend/.env.example`；
- `BACKEND_URL` 本地要有默认值 `http://localhost:8000`，否则 `npm run build`（`verify.sh` 第 4 项）会失败；线上值按部署手册在构建时注入。

## 13. 表单、模型配置和输入体验

### 13.1 表单规则

- 必填项、格式、长度和限制在提交前可见；
- 校验错误靠近对应字段；
- 提交失败后保留用户输入；
- 多步骤表单保存草稿或清楚说明离开会丢失；
- 文本框支持合理的粘贴和换行；
- 错误不只用红色表达，还需文字说明。

### 13.2 模型和供应商配置

- 默认模型必须真实存在于可选列表；
- 已保存但暂时不可用的模型要显示“不可用”，不能偷偷切换到第一项；
- 模型名称、能力、成本提示和限制应来自统一配置；
- 配置变化后，当前任务使用了哪个版本应可追溯；
- 用户看不到的内部模型路由不应伪装成用户明确选择。

### 13.3 文件上传

- 上传前说明格式、数量和大小限制；
- 校验扩展名之外，还要依赖后端验证真实类型；
- 显示上传进度、失败原因和重新上传；
- 允许删除或替换尚未提交的文件；
- 大文件使用后端支持的分片或直传方案；
- 私有文件不能依赖永久公开 URL。

## 14. Agent 产物展示

### 14.1 通用产物模型

前端不应只为一种图片结果写死页面。建议统一考虑：

```ts
type Artifact = {
  id: string;
  kind: "text" | "image" | "video" | "audio" | "file" | "json";
  name: string;
  status: "processing" | "ready" | "failed";
  url?: string;
  previewUrl?: string;
  mimeType?: string;
  size?: number;
  createdAt: string;
  metadata?: Record<string, unknown>;
};
```

项目可以扩展，但同一类产物的预览、下载、失败和加载方式应统一。

### 14.2 图片、视频和音频

- 图片有占位、加载失败、放大查看和下载；
- 视频有封面、加载中、播放失败和基本控制；
- 音频有时长、播放状态和下载；
- 多媒体尺寸未知时要预留比例，避免页面跳动；
- 临时 `Object URL` 使用后及时释放；
- 外链资源需要考虑过期、跨域和权限失败；
- 生成中产物不能伪装为最终完成。

### 14.3 结果与调试信息分层

默认界面首先服务普通用户：结果、状态、下一步操作在前。

请求 ID、原始 JSON、详细步骤和日志放入可折叠的“详情”或开发模式。不要把开发调试台直接当成产品界面。

## 15. 设计系统与视觉实现

### 15.1 设计来源优先级

1. 已确认的设计系统和设计稿；
2. PRD 中的品牌、用户和场景要求；
3. 已确认的参考产品，但不得直接复制其受保护资产；
4. 第三方设计系统（产品经理给网址，AI 抓取其中的 DESIGN.md / token）；
5. 本手册的中性默认方案。

如果没有设计稿，AI 应先输出一个简短的视觉方向：颜色、字体、密度、圆角、页面结构和关键组件，再实现首个代表页面供确认。

**第三方设计系统（如 Refero 等风格参考站）**：产品经理可能只给一个网址。AI 应主动用命令行抓取解析，而不是让产品经理口述。注意抓取边界——SSR 页面能直接拿到完整 DESIGN.md；纯 SPA、需登录或反爬的页面可能只能拿到空壳，此时让产品经理把关键截图和 DESIGN.md 文本直接发在对话里，由 AI 存入 `docs/设计参考/`。DESIGN.md 里的颜色/圆角/间距/阴影 token 可直接落为 Tailwind `@theme`。版权上，开源/可商用的设计系统可复用 token，受版权保护的只能借鉴风格。

**字体规则（中文产品必看）**：设计系统自带的西文字体多不含中文字形，且部分为商业授权（如 Basier Circle），使用前先确认授权；商业授权的不能直接打包。落地时用官方免费替代（Inter、Plus Jakarta Sans 等）+ 中文系统字体 fallback（PingFang SC / Microsoft YaHei / Noto Sans CJK SC）。`next/font` 加载的字体在构建时下载并自托管，运行时不请求外部 CDN；但 `next/font/google` 构建时要访问 Google，国内网络下 `npm run build` 可能因此失败。国内构建环境优先用 `next/font/local` 加载放进仓库的字体文件（先确认字体授权允许分发）。保留"双字体"思路（正文 + 展示标题），但中文字形统一走系统字体。

### 15.2 最低设计系统

即使是 MVP，也至少统一：

- 主色、背景色、文本色、边框色和状态色；
- 字号层级和行高；
- 4 或 8 像素节奏的间距；
- 圆角和阴影层级；
- 按钮、输入框、卡片、弹窗、提示和标签；
- hover、focus、disabled、loading、error 状态；
- 页面最大宽度和内容密度。

### 15.3 组件层级

- 基础组件：Button、Input、Select、Dialog；
- 复合组件：FileUploader、TaskStatus、ArtifactPreview；
- 业务组件：VideoGenerationForm、WorkflowRunPanel；
- 页面：组织布局和业务流程，不堆积所有底层细节。

不要为了“复用”过早制造需要十几个参数的万能组件。

### 15.4 图标和文案

- 使用统一图标库，不混用多套风格；
- 不用表情符号替代正式功能图标；
- 只有图标的按钮必须有可访问名称和悬停说明；
- 按钮文案使用动作和结果，例如“生成分镜”，不要只写“确定”；
- 状态文案使用产品语言，不暴露内部技术术语。

## 16. 响应式与移动端

### 16.1 默认验收宽度

如 PRD 未另行规定，至少检查：

- 390px：常见手机宽度；
- 768px：平板或窄窗口；
- 1280px：常见桌面工作区；
- 1440px：较宽桌面。

### 16.2 移动端规则

- 桌面侧栏在手机上应变成抽屉或底部导航；
- 抽屉关闭时不能残留透明遮挡层；
- 弹窗在小屏幕可滚动，主要操作始终可触达；
- 表格优先改成卡片、分组或横向受控滚动；
- 固定宽度媒体不得撑破屏幕；
- 触控目标建议不小于 44×44px；
- 键盘弹出时，输入框和提交按钮不能完全被遮挡；
- 页面不得出现无意的横向滚动。

响应式不能只看首页。核心业务流程的每一个页面和弹窗都要检查。

---

## 17. 无障碍基础要求

MVP 阶段至少做到下面几条，并纳入第 21.4 节的浏览器检查：

- 所有核心操作可以用键盘完成，焦点位置清晰；弹窗有焦点约束，关闭后焦点回到触发处；
- 所有表单项有关联 Label，错误提示能被辅助技术识别并定位到字段；
- 只有图标的按钮有可访问名称；
- 状态不只靠颜色表达，文本与背景有足够对比度；
- Agent 关键进度使用适度的 live region，避免每个 Token 都被朗读。

## 18. 安全与隐私底线

### 18.1 禁止放入前端

- 模型服务 API Key；
- 数据库密钥；
- 第三方服务私钥；
- 私密系统提示词；
- 后端管理员凭证；
- 只应服务端知道的业务规则。

### 18.2 鉴权

- 默认方案：登录（邀请码或账号）成功后由后端签发会话，放在 Secure、HttpOnly、SameSite 合理配置的 Cookie 中；前端不自行保存 token。上线部署手册的登录章节以此为准；
- 不得将长期访问令牌放入 Local Storage 或 Session Storage；
- 同时考虑 CSRF、XSS、会话过期和跨设备退出；
- 权限判断必须由后端执行，前端隐藏按钮不等于权限控制。

### 18.3 内容安全

- 用户或模型生成的 HTML 默认视为不可信；
- Markdown 渲染需限制危险标签和链接；
- 外部链接明确打开行为，必要时增加安全属性；
- 文件名、富文本和 URL 不能直接拼入 DOM；
- 日志、埋点和报错中避免记录完整提示词、隐私文件和密钥。

### 18.4 高成本操作

涉及真实扣费、发布、群发、删除、覆盖和外部系统写入时：

- 前端明确展示影响；
- 用户进行最终确认；
- 后端再次校验权限和幂等性；
- 页面保留结果或审计入口。

---

## 19. 性能原则

先测量，再优化。MVP 至少做到：

- 首屏不加载当前页面用不到的大型库，富编辑器、图表、视频工具按需加载；
- 图片和媒体预留尺寸，减少布局跳动；
- 流式内容节流或批量更新，大列表分页；
- 相同接口不被多个组件重复请求，大型二进制文件不长期放在 React State。

不能用"以后优化"掩盖明显卡顿、内存泄漏和页面冻结。

## 20. 日志、监控和产品分析

- 前端错误至少记录：时间、页面、错误码、请求 ID 或任务 ID、应用版本、是否可恢复；不得上传用户完整输入、生成内容、私密文件或凭证（`AGENTS.md` 第 2 节第 6 条）。
- 产品埋点只在 PRD 或指标方案明确后实施，事件名表达业务行为（如 `generation_submitted`、`artifact_downloaded`）；埋点不能阻塞核心操作，埋点失败不能导致生成任务失败。
- 接入 Sentry 等第三方监控或分析服务前，先告知费用量级并等产品经理确认（第 4 节 C 层）。

## 21. 测试与真实预览

### 21.1 最低自动检查

每个可交付阶段至少执行：

```bash
npm run lint
npm run typecheck   # 项目如无该脚本，应通过 tsc --noEmit 或等价方式补齐
npm run test
npm run build
```

如果某项暂未配置，AI 应在阶段文档中说明并补齐合理的最低配置，不能直接写“跳过”。

根目录 `verify.sh` 会依次调用 `npm run lint`、`npx tsc --noEmit`、`npm test -- --run`、`npm run build`，脚本名必须与之对应：

- Next.js 16 起已移除 `next lint`，`next build` 也不再自动跑 ESLint。`lint` 脚本必须直接调用 `eslint .`；已有项目若仍写着 `next lint`，升级后要改，否则 `verify.sh` 第 4 项失败。
- `test` 脚本必须一次跑完就退出（Vitest 用 `vitest run`），不能停在监听模式。

### 21.2 测试分层

| 层级 | 重点 |
|---|---|
| 单元测试 | 状态映射、数据转换、校验、错误归一化 |
| 组件测试 | 表单、按钮状态、空/错/加载、确认交互 |
| 集成测试 | API 适配层与页面业务流程 |
| E2E 测试 | 一个真实用户从进入页面到获得结果的核心闭环（引入 Playwright 后；之前用可重复的"照着点"步骤代替） |
| 人工预览 | 视觉、文案、媒体、响应式、浏览器行为 |

### 21.3 核心业务闭环

每个阶段至少有一条可以真正操作的闭环，例如：

```text
进入生成页
→ 填写输入
→ 成功提交
→ 看到任务运行
→ 处理用户确认（如有）
→ 看到最终产物
→ 刷新页面后仍可恢复
```

仅证明按钮能点击、Mock 数据能展示，不算业务闭环。

### 21.4 浏览器检查

AI 在交付前必须真实启动前端和后端，并用脚本化浏览器完成下面的检查。默认写一个一次性的 Playwright 脚本（只当截图与检查工具用，不等于引入 E2E 测试套件），或使用等价工具：

- 在 390、768、1280、1440 四个宽度打开核心流程的每个页面和弹窗并截图，截图存入 `docs/evidence/阶段3-N/`；
- 收集浏览器 Console 错误和失败的网络请求：交付时 Console 错误为零，失败请求逐条说明原因；
- 检查加载、空、错误、禁用和成功状态，以及侧栏、弹窗、下拉框和滚动；
- 走通真实后端接口和流式链路，检查图片、视频、音频和下载；
- 检查刷新、返回、断网后的恢复。

这些截图和检查结果支撑是否表第 7 项。生产构建成功只能证明工程可构建，不能替代真实页面检查。

### 21.5 交付判定

以下任一情况存在时，不得直接宣布“完成”：

- Lint 或类型检查仍有未解释错误；
- 核心接口仍是 Mock；
- 核心页面在目标尺寸不可用；
- 失败状态会丢失用户输入；
- 重复点击会创建多个任务；
- 刷新后正在运行的任务无法恢复；
- Console 持续报错；
- 实现与确认的设计或 PRD 明显不一致。

是否表十项内的问题不能带着交付，必须先解决。十项之外的已知问题（如某个非核心页面的视觉细节），列入阶段开发文档的"已知问题"，写明影响、临时处理和后续计划，由产品经理确认。

**关键业务规则未冻结时**（评分公式、判定阈值、话术标准等尚未定稿）：AI 不应因此卡住开发，而应——
- 用临时规则跑通全链路，界面对用户显式标注"模拟/临时"；
- 把规则做成可配置（JSON / 表），业务冻结后只改配置、不改代码；
- 在交付清单中明确列出"哪些业务规则仍待冻结"，不得当作已完成。

**每个前端子阶段结束时必须做完以下事项**，然后才能填是否表：

1. 真实启动前端和后端，按第 21.4 节完成浏览器检查；
2. 对接真实后端和真实模型，至少跑通一条核心闭环（真实模型冒烟，是否表第 3 项）；没有真实 Key 时如实写"待验"，不得用 Mock 冒充；
3. 确认 `scripts/restart-check.sh` 存在且适用于当前项目；本子阶段新增了需要持久化的数据时，同步更新这个钩子；
4. 运行根目录 `./verify.sh 阶段3-N`。它会跑前端 Lint、类型检查、测试、生产构建和密钥扫描，并调用 `scripts/restart-check.sh` 判断重启后数据是否还在。是否表第 2、4、5、6 项抄脚本结果，不得手填；
5. 更新 README 的启动与验证方法（是否表第 8 项）和 `docs/项目状态.md`（是否表第 9 项）；
6. 交付证据包，存放在 `docs/evidence/阶段3-N/`，共四样：桌面与移动端关键页面截图、产品经理能自己打开的预览地址与"照着点"步骤、是否表、`verify-输出.txt`。其余命令输出不放进证据包，追问时再给。

是否表任一项为"否"，不得宣布阶段完成。汇报时写清已完成、检查结果、未完成和已知问题；不要因为构建成功就宣布页面完成，也不要用 Mock 数据代替最终联调。

### 21.6 为上线做的准备

阶段 3 结束前，把 `next.config` 设为 `output: "standalone"`，并把前端指向的后端地址做成构建时注入的环境变量 `BACKEND_URL`（本地默认 `http://localhost:8000`）。其余部署步骤（静态资源补齐、启动命令、同源代理、HTTPS）见上线部署手册中前端应用单独部署一节，阶段 4 再读。

## 22. 分阶段开发原则

不要按“先写完所有页面，再一次性接接口”拆阶段。应按用户可验证的业务闭环拆分。

> 以下“前端子阶段 0~4”是第 22 节内的**前端内部子阶段**，对应全局流程（AGENTS.md 第 7 节）中“阶段 3 正式前端”的拆分，与全局阶段编号（阶段 0~5）无关。

### 前端子阶段 0：适配与契约

- 读第 0 节列出的项目内文档，按第 0 节判断阶段 2 留下的界面是纵向切片、临时验收界面还是没有界面；
- 输出《前端适配声明》，写明上一步的判断和处理方式；
- 明确路由、页面清单、设计方向和接口契约；
- 建立任务状态表和核心验收路径；
- 标记尚未确认的假设。

### 前端子阶段 1：可运行骨架

阶段 2 已有纵向切片界面时，本子阶段与子阶段 2 合并，在已有界面上补齐骨架；阶段 2 只有临时验收界面时，在本子阶段把它废弃并记录。

- 建立工程、布局、导航、设计变量和通用组件；
- 接通基础环境配置和 API 客户端；
- 完成一个代表页面；
- 确保桌面和移动端基本布局正确；
- 配置 Lint、类型检查、测试和构建。

### 前端子阶段 2：第一条真实闭环

- 完成一个核心输入流程；
- 对接真实创建任务接口；
- 展示队列、运行、成功和失败；
- 展示至少一种真实产物；
- 写出可重复的"照着点"验收步骤；引入 Playwright 后补核心 E2E。

### 前端子阶段 3：Agent 完整交互

- 接入流式输出或轮询；
- 支持等待用户确认；
- 支持取消、重试、断线和刷新恢复；
- 完善多任务、历史记录或任务中心（按 PRD）；
- 覆盖部分成功和未知状态。

### 前端子阶段 4：质量与发布准备

- 完成响应式、无障碍和多媒体检查；
- 处理性能、错误监控和隐私；
- 与真实后端做完整联调；
- 清理 Console、Lint、类型和测试问题；
- 输出发布说明和已知问题。

具体项目可以合并阶段，但每个阶段都应有可运行、可查看、可验收的结果。前端只通过后端 API 调用业务能力；已经验证过的纵向切片界面在原地延续，不重复建设平行界面。每个子阶段按第 21.5 节交付。

## 25. 产品经理验收（AI 转述）

产品经理不看代码，也不自己判断 Lint、类型检查、测试、构建这类技术项。AI 在每个前端子阶段结束时这样转述：

1. 打开证据包里的预览地址，按"照着点"步骤从进入页面一直走到拿到一个真实结果；
2. 对照截图看：手机和电脑上是否都能走完；第一次打开时有没有把"加载中"显示成"没有数据"；失败后知不知道怎么恢复；刷新后任务还在不在；重复点击会不会创建多个任务或重复扣费；
3. 看是否表有没有"否"；测试、密钥、重启恢复、构建四项以 `verify-输出.txt` 为准，不凭感觉判断；
4. 发现异常就截图发给 AI。
